# Stage 1: Building the Data Layer — Calima Data

Search Engine Project · Big Data · Grado en Ciencia e Ingeniería de Datos · ULPGC

Builds the data layer for a simple search engine: a **datalake** that stores
raw/cleaned books downloaded from [Project Gutenberg](https://www.gutenberg.org/),
and **datamarts** (metadata + inverted index) that expose that content for
fast querying. The pipeline and its benchmarks are implemented in three
languages — **Python, Java and Node.js** — so the datalake and inverted-index
storage strategies can be compared independently of the implementation
language.

## Repository structure

```
worker_python/   Reference implementation (requests + sqlite3), benchmarked with pytest-benchmark
worker_java/     Maven project (java.net.http + sqlite-jdbc), benchmarked with JMH
worker_node/     Node.js port (fetch + node:sqlite), benchmarked with a hrtime harness
sample_data/     Small slice of real pipeline output, see sample_data/README.md
datalake/        Raw book storage (git-ignored, generated by the pipeline)
datamarts/       Metadata + inverted index (git-ignored, generated by the pipeline)
control/         Control-layer tracking files (git-ignored, generated by the pipeline)
```

Each language writes the **real** pipeline output to its own namespaced
subfolders (`datalake/time_based_java/`, `datalake/book_based_node/`, ...)
and its own control files (`control/downloaded_books_java.txt`, ...). This
keeps the three implementations from clobbering each other while processing
the same dataset, so the comparison stays about language + storage
structure, not shared state. The three **benchmarks**, by contrast, run
against fully isolated temporary directories that are deleted afterwards.

## Datalake: 3 storage structures (implemented in all 3 languages)

- **time-based**: `datalake/<YYYYMMDD>/<HH>/<id>.{header,body}.txt`
- **book-based**: `datalake/book_based/books/<id>/{header,body}.txt`
- **range-based**: `datalake/range_based/batch_<lower>_<upper>/<id>.{header,body}.txt`

## Datamarts

- **Metadata** (`worker_python/datamart_metadata.py`): regex-parsed from each
  book's header (title, author, language) into a SQLite `books` table.
- **Inverted index** — 3 structures benchmarked, each with its own control
  file so re-runs don't re-index a book twice:
  - Monolithic JSON file (`datamart_index.py` / `DatalakeBenchmark`-style port)
  - Hierarchical folders, one `.txt` per term (`datamart_index_folder.py`)
  - Normalized SQLite table `postings(term, book_id)` (`datamart_index_sqlite.py`)

  SQLite was chosen over MongoDB (the third example in the assignment
  brief) to keep the whole pipeline dependency-free (embedded DB, no server
  to run) while still comparing a "real" indexed database against the two
  file-based approaches.

## Control layer

Plain-text control files under `control/` (one book ID per line) track which
books have been downloaded and which have been indexed, per structure. This
prevents duplicate downloads/indexing on repeated runs and lets the pipeline
resume after an interruption.

## Setup & how to run

### Python (reference implementation)

```bash
cd worker_python
python -m venv venv && venv\Scripts\activate   # or: source venv/bin/activate
pip install -r requirements.txt

python datalake.py              # download sample books into the 3 datalake structures
python datamart_metadata.py     # extract metadata -> datamarts/inverted_index.db (books table)
python datamart_index.py        # build the monolithic JSON index
python datamart_index_folder.py # build the folder-hierarchy index
python datamart_index_sqlite.py # build the SQLite postings index

pytest test_benchmark.py -v --benchmark-columns=min,max,mean,median,stddev
pytest test_index_benchmark.py -v --benchmark-columns=min,max,mean,median,stddev
```

### Java

Maven project targeting **Java 11**, benchmarked with [JMH](https://openjdk.java.net/projects/code-tools/jmh/).
Benchmarks live in `src/test/java`, as in the course's `jmh-project` example.

```bash
cd worker_java

mvn clean compile
mvn exec:java -Dexec.mainClass=org.calima.Datalake -Dexec.classpathScope=compile  # download sample books

mvn clean test-compile exec:java    # runs the whole JMH suite (both benchmarks)
```

To run a single benchmark class, pass a regex through to the harness:

```bash
mvn clean test-compile exec:java -Dexec.args="IndexBenchmark"
```

The benchmark classes can also be launched directly from IntelliJ with the
[JMH plugin](https://plugins.jetbrains.com/plugin/7529-jmh-java-microbenchmark-harness).

### Node.js

Requires Node.js 22+ (uses the built-in `node:sqlite` module, no npm install needed).

```bash
cd worker_node
node datalake.js          # download sample books
node datalakeBenchmark.js # datalake structure benchmark
node indexBenchmark.js    # inverted-index benchmark
```

## Benchmark results (reference run)

Captured on a single development machine — re-run before writing the final
report, numbers will vary by hardware.

**Methodology.** All three languages measure the same unit of work: writing
1000 synthetic books under one datalake layout, and inserting one 500-term
book (450 terms already present, 50 new) into an index pre-populated with a
5000-term vocabulary. Every run discards warmup rounds before measuring —
2 warmup + 5 measured for the datalake benchmark, 3 warmup + 8 measured for
the index benchmark — because the first rounds pay JIT compilation (JVM),
native-library loading (sqlite-jdbc) and OS disk-cache warming, which
otherwise swamp the measurement. Java uses JMH, Python uses
`pytest-benchmark`'s `pedantic` mode, Node.js uses a `process.hrtime` harness.

### Datalake structures — time to write 1000 books, mean ms/op

| Language | time_based | book_based | range_based |
|---|---|---|---|
| Python       | 1509.4 | 1151.8 | 1194.7 |
| Java (JMH)   | 1209.1 | 1011.4 | 1029.7 |
| Node.js      | 1613.4 | 1788.2 | 1542.9 |

Java's JMH confidence intervals (±154, ±515, ±332 ms respectively) overlap
each other, so **within Java the three layouts are not statistically
distinguishable**. Python and Node.js both make `time_based` the slowest
layout, which is consistent with it concentrating all 1000 files into a
single `YYYYMMDD/HH` directory while the other two spread them across many.

### Inverted index — time to insert a 500-term book, mean ms/op

| Language | SQLite postings | JSON monolithic | Folder hierarchy |
|---|---|---|---|
| Python       | 1.44 | 34.90 | 215.11 |
| Java (JMH)   | 1.28 | 14.48 | 182.95 |
| Node.js      | 1.82 |  5.59 | 572.63 |

The ranking is identical in all three languages: **the SQLite postings table
beats both file-based structures by two orders of magnitude**, monolithic
JSON sits in the middle, and the folder-per-term hierarchy is slowest because
each update opens, reads and rewrites hundreds of small files. The spread
between structures (≈140×) dwarfs the spread between languages (≈1.4× for
SQLite), which is the central result of this stage: **the storage structure
dominates, the language runtime is secondary**.
